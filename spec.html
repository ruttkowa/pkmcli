PKM TUI System Specification

Project Goal

Build a local-first Personal Knowledge Management (PKM) application inspired by Neovim, Zellij, LazyGit and Obsidian.

The application is not an editor. It is a navigation, organization and knowledge management layer built around Markdown files.

Editing is delegated to an external editor.

Core Principles

  • Local-first
  • Markdown-only
  • Git-first
  • No AI integration
  • No attachments
  • No plugin system in v1
  • No graph view in v1
  • No query language in v1
  • Keyboard-first
  • Mouse-capable
  • Opinionated workflow

Knowledge Management Model

The system follows a PARA-inspired workflow.

States

  • Inbox
  • Projects
  • Areas
  • Research
  • Archive

Rules

  • All new notes are created in Inbox.
  • Notes must be explicitly promoted.
  • Maximum of 4 active projects.
  • Archive is the final inactive state.

Lifecycle

 Inbox ├──► Project │ │ │ └──► Archive │ ├──► Area │ │ │ └──► Archive │ └──► Research │ └──► Archive

Storage Format

Files

All notes are Markdown files.

Filename format: 

 <ID> <Title>.md

Example: 

 202606241530 Docker.md

Frontmatter

 --- id: 202606241530 title: Docker created: 2026-06-24T15:30:00 updated: 2026-06-24T15:45:00 state: research project: tags: - linux - containers ---

Vault Structure

 vault/ ├── notes/ ├── templates/ ├── .pkm/ │ ├── config.toml │ ├── projects.toml │ └── index.db └── .git/

No content-based folder hierarchy. Organization happens through metadata, tags and states.

Tags

  • Tags are stored in frontmatter.
  • Tags replace most folder organization.
  • Tags are first-class organizational elements.

Example:

 tags: - linux - homelab - server

Links

 [[Docker]] [[Docker|Container Runtime]]

Behavior

  • Links can point to non-existing notes.
  • Missing notes are created when opened.
  • Aliases are supported.

Backlinks

No graph visualization.

Search

Version 1

  • Fuzzy search
  • Title search
  • Content search
  • Tag search

Future

  • Query language
  • Saved searches
  • Dataview-like capabilities

Templates

Templates are stored as Markdown files.

Supported Variables

 {{id}} {{title}} {{created}} {{updated}}

Future Variables

 {{input:name}} {{input:project}}

Tasks

Tasks are Markdown checkboxes. 

 - [ ] Install Docker - [x] Configure SSH

No custom task syntax.

Tasks may be indexed by the system.

Editor Model

The application is not a text editor.

Editing is delegated to a configurable external editor.

Examples:

  • nvim
  • vim
  • helix
  • emacs

Mouse is supported but not required.

Supported Actions

  • Focus pane
  • Resize pane
  • Open link
  • Select sidebar item

Navigation Model

Navigation behaves like a web browser.

Default Open

  • Click
  • Enter

Replaces current pane content.

Open In New Pane

  • Ctrl + Click
  • Ctrl + Enter

History

  • Back
  • Forward
  • History is stored per pane

Application Startup

When the application starts:

  • Restore previous session.
  • Restore previous pane layout.
  • Restore last opened note.
  • Open in read mode.

Git Integration

The vault is expected to be a Git repository.

Future UI integration may include:

  • Modified notes
  • Uncommitted changes
  • Status overview

Index Architecture

Approach

Hybrid indexing model.

Startup

  • Load persisted index.
  • Perform validation scan.

Runtime

  • File watcher monitors vault.
  • Incremental updates.
  • Persistent cache.

Indexes

  • Full-text index
  • Tag index
  • Link index
  • Backlink index
  • Metadata index

Command System

Commands are executed through a command palette.

Activation: 

 :

Examples

 :new "Docker" :open docker :search docker :move docker → project/homelab :archive docker :split docker

Features

  • Autocomplete
  • Fuzzy matching
  • Command suggestions
  • Note suggestions
  • Tag suggestions
  • Project suggestions

Command DSL

General Form

 :<command> [target] [arguments] [→ destination]

Examples

 :new "Docker" :open docker :move docker → project/homelab :archive docker :split docker

State Model Direction

Future implementation should be state-driven.

Commands mutate state. State emits events. UI reacts to state changes.

Pipeline

 Input ↓ Parser ↓ Resolver ↓ Command ↓ State Update ↓ Event ↓ UI Refresh

Explicit Non-Goals

  • No AI integration
  • No attachment management
  • No graph visualization
  • No plugin system
  • No embedded editor
  • No canvas system
  • No PDF management
  • No image management
  • No custom task language
  • No query language in v1
