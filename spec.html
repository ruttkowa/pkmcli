PKM TUI System Specification

Project Goal

Build a local-first Personal Knowledge Management (PKM) application inspired by Neovim, Zellij, LazyGit and Obsidian.

The application is not a full editor. It is a navigation, organization and knowledge management layer built around Markdown files.

For quick changes it ships a deliberately minimal built-in inline editor (open a note and press e, save with Ctrl+S). For heavier editing you use your own external editor directly on the Markdown files under vault/notes/ — the file watcher syncs changes back into the viewer live. The app never launches or embeds a full text editor.

Core Principles

  • Local-first
  • Markdown-only
  • Git-first
  • No AI integration
  • No attachments
  • No plugin system in v1
  • No graph view in v1
  • No query language in v1
  • Keyboard-first
  • Mouse-capable
  • Opinionated workflow

Implementation Status (as of 2026-07-09)

This document is the original design specification. The sections below describe the intended system; not everything is built yet. Shipping today:

  • Vault with Inbox / Projects / Areas / Research / Archive states; PARA-style promotion; max 4 active projects; project detail pages with history; assign-to-project (Shift+P).
  • SQLite index (.pkm/index.db) with FTS5 full-text search; live file watcher with incremental updates.
  • Command palette (:) with fuzzy autocomplete: :new, :open, :search, :move, :archive, :delete, :split, :close, :import, :config, :theme, :insert, :new project, :new template, :help, :quit.
  • View mode: block-cursor navigation, wiki-link following, checkbox toggle (cursor + Enter, or mouse click), code-block copy via OSC 52, H1–H6 heading styles, mouse-wheel scrolling, and a live save-status footer.
  • Built-in inline editor (e): Markdown list/checkbox continuation, wiki-link autocomplete, tag / state / project fields, undo & redo, save-status footer.
  • Configurable keybindings; config export / import; user-defined insert variables; session & pane-layout restore; horizontal splits with per-pane history.
  • Soft-delete with Ctrl+Z undo (a durable disk-based trash is still planned).

Active and planned work is tracked in GitHub Issues on the ruttkowa/pkmcli repository, not in this spec. Notable not-yet-built items include a durable soft-delete/trash, text selection & clipboard copy/paste, a task-overview view, and a backlinks pane. Inline task metadata (results, completion dates) is now built — see Tasks below.

Knowledge Management Model

The system follows a PARA-inspired workflow.

States

  • Inbox
  • Projects
  • Areas
  • Research
  • Archive

Rules

  • All new notes are created in Inbox.
  • Notes must be explicitly promoted.
  • Maximum of 4 active projects.
  • Archive is the final inactive state.
  • Areas, Research, and Archive may contain metadata folders (not physical directories).
  • Project membership is an independent soft link and does not change a note's location or folder.

Lifecycle

 Inbox ├──► Project │ │ │ └──► Archive │ ├──► Area │ │ │ └──► Archive │ └──► Research │ └──► Archive

Storage Format

Files

All notes are Markdown files.

Filename format: 

 <ID> <Title>.md

Example: 

 202606241530 Docker.md

Frontmatter

 --- id: 202606241530 title: Docker created: 2026-06-24T15:30:00 updated: 2026-06-24T15:45:00 state: research project: tags: - linux - containers ---

Vault Structure

 vault/ ├── notes/ ├── templates/ ├── .pkm/ │ ├── config.yaml │ ├── projects.yaml │ └── index.db └── .git/

No content-based folder hierarchy. Organization happens through metadata, tags and states.

Tasks

Tasks are Markdown checkboxes: - [ ] / - [x]. Plain checkboxes with no metadata remain fully valid — nothing is rewritten on load, only on an actual toggle. 

 - [ ] Install Docker - [x] Configure SSH

A checkbox line may optionally carry a completion date and a result, in this canonical order: text, then ✅ YYYY-MM-DD if done, then --> result if set. 

 - [x] Ship the thing ✅ 2026-07-10 --> shipped in v2 - [x] Read paper ✅ 2026-07-10 --> [[202606241530 Notes]]

The completion date is stamped automatically when a task is toggled done, and stripped when toggled back to undone (overwritten by repeated toggles, not accumulated). A result is free text following -->; if it parses as a [[wikilink]] it renders and opens as a link like any other wikilink. This is a deliberate, minimal departure from "no custom task syntax" below — everything else about the task model (indexing, no query language) is unchanged.

Tasks may be indexed by the system.

GitLab Issues (read-only)

Configured GitLab projects appear as virtual sections in the Tasks overview. Open issues are read-only, never become notes or enter the SQLite note index, and are cached in .pkm/issues.json. Authentication is read from PKM_GITLAB_TOKEN only. Issues fetch once on first Tasks open and refresh manually with r; details fetch comments live and degrade to cached issue data when offline.

Editor Model

The application is not a full text editor. Two editing paths exist:

  • Built-in inline editor — a lightweight editor for quick edits (open a note, press e; save with Ctrl+S). It handles Markdown list/checkbox continuation, wiki-link autocomplete, tag/state/project fields, undo/redo and a save-status footer. Intentionally minimal — not a replacement for a real editor.
  • Your external editor — edit the Markdown files under vault/notes/ directly in nvim, vim, helix, emacs or anything else. The file watcher picks up the changes and refreshes the viewer without a restart. The app does not launch the external editor and has no configurable "editor" setting.

Command DSL

General Form

Examples

State Model Direction

Future implementation should be state-driven.

Commands mutate state. State emits events. UI reacts to state changes.

Pipeline

 Input ↓ Parser ↓ Resolver ↓ Command ↓ State Update ↓ Event ↓ UI Refresh
